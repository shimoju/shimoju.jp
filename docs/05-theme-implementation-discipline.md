# 5. Hugoテーマの実装規律

状態：確定（2026-09-17）。本資料内のQ1〜Q9と、規律・進捗フォーマット・開始用プロンプトの一式についてユーザーと認識一致を確認済み。Q6はユーザー指定によりJSONを採用。資料4のQ番号とは独立した番号を使う。

## 目的と適用範囲

[実装要件](04-theme-implementation-requirements.md)を満たすshshの実装中に、モックの表示・操作を尊重しながら、同じ役割を一緒に変更できる構造を保つ。また、実装中に見つけた問題を判断・修正・再検証につなげる。

対象はCSS、ブラウザ用TypeScript、Hugoテンプレートと、それらを用いる実装・レビューの進め方。formatter・linterで検知する問題を本資料の規律として重複定義しない。開発ツールと検証範囲は資料4に従う。

## 仕様と実装者の裁量（Q1）

- 表示・操作を維持する内部構造の整理は、実装者が自律的に進める。
- モックと異なる見た目・操作を生む変更は、変更案と影響範囲を示して判断を求める。同じ役割に見える要素を揃える場合も、見た目が変わるならこの対象に含める。
- 資料4で明示されたモックからの変更は、既存の合意に従って実装する。合意済み事項の再承認を求めない。
- 実装中のモックは凍結した比較基準として残し、承認した差分を記録する。実装結果に合わせてモックを黙って変更しない。
- モックのデザイン上の不整合や不適切な実装を見つけた場合、コピーによって持ち込まず、根拠を確かめて扱いを判断する。表示・操作を維持して是正できる内部実装は自律的に直し、仕様の変更や意図の判断が必要なら相談する。

## 役割に基づくトークン化と共通化（Q2）

- 共通化の基準は「今後も一緒に変更すべき役割」とする。同じ役割には共通のルールを適用し、数値が偶然同じという理由だけでは統合しない。
- CSS変数を用い、基礎となる尺度と用途を表すトークンを必要に応じて分ける。すべての数値の変数化や、すべての部品への専用トークン追加は要求しない。
- 本文組版とUI寸法など、資料3で区別した尺度・役割を保つ。共通化により別々に調整すべきものを結び付けない。
- 個別の補正には理由を残し、共通ルールとの関係を説明できる状態にする。説明できない差は、正しいと決めつけず調査・判断の対象にする。

モックでは、見出しとラベルの行高はともに1.5でも役割別トークンであり、タイトルと日付の間隔は一覧・記事・Archivesで共有されている。このような役割の関係を確認してから整理する。

## 責務に基づく分割（Q3）

- CSSはトークン、本文組版、共通レイアウト、部品などの責務を基準に分割する。具体的なファイル構成は実装で決める。
- TypeScriptは配色、コピー、共有などの機能と責務を基準に分割する。モックのファイル名や構成をそのまま設計と見なさない。
- Hugoテンプレートも対象とし、同じ表示・生成規則を共有する。CSS変数だけを共有してHTML構造や生成処理の複製を残すことを、共通化の完了とはしない。
- CSS・TypeScriptは資料4のHugo Pipes構成で処理する。ソースの分割と配信ファイル数は別に判断する。
- ファイル数・行数を基準にした機械的な分割は避ける。分割によって表示・操作や実行タイミングに必要な関係を壊さない。

## レビューと反復（Q4）

- 共通設計が代表画面で成立した段階と、全画面が揃った段階でレビューする。重大な矛盾は、その段階を待たず発見時に提示する。
- 指摘には現状・根拠・影響・推奨案を残す。判断が必要な変更は承認後に修正し、再検証する。
- 判断待ちの部分に依存しない作業は続行する。判断を暗黙に代行して後続作業を確定させない。
- 周回数は固定せず、未解決事項を追跡する。初回実装を終えただけで完了とはしない。
- 途中のレビュー時にも、どこまで完了しているか、何が未完了か、どこから再開するかを把握できるよう、後述のJSONで進捗を管理する。

## 最終目標と未確認事項（Q5）

- `/goal`へ渡す最終目標は、資料4の移行完了とする。初回実装に加えて、指摘・判断・修正・再検証を含む。
- 人の判断・確認が必要な地点を途中に設ける。実機確認やCloudflare Pages上の検証を含め、コードの実装だけでは完了しない。
- 人による確認が必要な項目は、確認手順と証拠を用意して依頼する。未確認の項目を合格扱いしない。

## JSONによる進捗管理（Q6）

[06-theme-implementation-progress.json](06-theme-implementation-progress.json)を、進捗確認・再開の起点とする。会話内の報告や一時的な作業リストだけに進捗を残さない。JSONには現在の状態と履歴の参照を保持し、長い検証報告や画像は別の成果物を参照する。

### 管理単位と更新時点

- 実装開始時に、資料4の全要件・補足・完了条件と本資料の規律を、レビュー・検証できる単位の作業へ対応付ける。ファイル数やコード量を進捗率として扱わない。
- 各作業に実装状態・検証状態・関連レビューを別々に持たせる。「実装した」「検証に合格した」「人の判断が済んだ」を区別する。
- 作業単位の終了時、検証後、判断後、中断前に更新する。指摘の発見時にも記録し、対応する作業との依存関係を更新する。
- 再開時はJSONとリポジトリの実際の変更・成果物を照合する。不一致があれば根拠を確認して状態を訂正し、記録だけを信じて完了扱いしない。
- IDは一度発行したら変更・再利用しない。完了した作業や解決済み指摘も削除せず残す。現在の概要と次の行動を更新し、履歴の全文を概要へ転記し続けない。

### フォーマット

パスは原則リポジトリルートからの相対パスとする。要件参照には資料名とQ番号または節名を含める。時刻にはタイムゾーン付きISO 8601形式を使い、未実施の時刻や判断は`null`にする。初期ファイルには計画作成作業と二つのレビューだけを置き、テーマ実装の着手・検証・承認を既成事実にしない。

| 項目 | 内容 |
| --- | --- |
| `format_version` | 進捗フォーマットの版。初版は1 |
| `updated_at` | 最終更新時刻 |
| `stage` | 現在の段階。`not_started` / `planning` / `representative` / `full_implementation` / `revision` / `final_verification` / `complete` |
| `summary` | 現在の到達点と残件の短い説明 |
| `latest_review_id` | 直近に結果が出たレビューのID。まだなければ`null` |
| `resume` | 次に扱う`task_id`と具体的な`action`。完了時は`task_id`を`null`にする |
| `tasks` | 作業。ID、要件、依存先、完了条件、実装・検証状態、成果物、検証・レビュー・判断待ちの参照、次の行動 |
| `findings` | 不整合・問題・提案と、それに対する判断・解決の記録 |
| `reviews` | 代表画面・全画面などのレビュー範囲、提出物、結果とユーザーの判断 |
| `verifications` | 自動検査・視覚確認・実機確認・構造レビューなどの実施記録 |

各配列の要素は次のフィールドを用いる。参照先が未作成なら参照IDを捏造せず、計画作成時に追加する。

| 配列 | フィールド |
| --- | --- |
| `tasks` | `id`, `title`, `requirement_refs`, `depends_on`, `acceptance_criteria`, `status`, `verification_status`, `artifact_refs`, `verification_ids`, `review_ids`, `blocked_by`, `next_action` |
| `findings` | `id`, `title`, `task_ids`, `status`, `requires_user_decision`, `observation`, `evidence_refs`, `impact`, `recommendation`, `decision`, `resolution_refs`, `verification_ids` |
| `reviews` | `id`, `title`, `task_ids`, `status`, `artifact_refs`, `verification_ids`, `finding_ids`, `decision`, `supersedes` |
| `verifications` | `id`, `task_ids`, `requirement_refs`, `kind`, `result`, `subject_ref`, `environment`, `procedure`, `evidence_refs`, `recorded_at`, `supersedes` |

- `tasks.status`は`not_started` / `in_progress` / `implemented` / `complete`。`verification_status`は`not_run` / `passed` / `failed` / `stale` / `blocked`。`depends_on`は作業ID、`blocked_by`は判断待ちなどの指摘ID、`review_ids`はその作業の完了に必要なレビューIDを持つ。複数検証のうち必要な一部が未実施・失敗・無効なら、全体を`passed`にしない。
- `findings.status`は`open` / `awaiting_decision` / `approved` / `rejected` / `resolved`。`approved`は提案の採用であり、修正完了ではない。却下は理由を記録し、元の問題が解消したことを意味しない場合は問題を未解決として残す。
- `reviews.status`は`not_ready` / `requested` / `changes_requested` / `approved`。承認にはユーザーの明示的な判断を記録する。無回答や自動検査の合格を承認に置き換えない。再レビューは新しいIDで追加し、`supersedes`に前回のIDを記録する。初回は`null`。作業の`review_ids`は現在必要なレビューへ更新し、過去の判断は元の記録に残す。
- `decision`は未判断なら`null`、判断後は`outcome`, `reason`, `decided_by`, `recorded_at`, `source`を持つオブジェクトにする。`source`にはユーザーの回答の引用または追跡可能な参照を残す。実装者の裁量で処理できる指摘では、その根拠と判断者を記録する。
- `verifications.result`は`passed` / `failed` / `blocked`。`subject_ref`で対象のコミットや未コミット差分・成果物を特定し、`environment`と`procedure`に再現に必要な環境・条件・手順を記録する。未実施は合格記録にせず、作業側の状態で示す。再検証は新しい記録を追加し、`supersedes`で前回の検証IDを参照する。初回は`null`。
- `tasks`を`complete`にするには、完了条件を満たす成果物・有効な検証結果と、必要なレビュー承認が揃い、判断待ち・未解決の阻害事項がないことが必要。作業を消す、条件を緩める、指摘を隠すことで完了にしない。
- `stage`を`complete`にするには、資料4の移行完了条件と本資料のレビュー・修正・再検証を満たすことが必要。人の確認待ち・外部環境の未検証は残件として明示する。

## レビューの提出物と通過条件（Q7）

代表画面レビューは、ホーム／一覧・記事・本文部品を両配色・PC／モバイルで比較できる状態で行う。表示比較と、トークンの役割およびCSS・TypeScript・テンプレートの責務分担の説明をセットで提出する。コードと対応し、同じ役割がどこで共有されるか、例外がどこにありなぜ必要かを追えるようにする。

レビューへの提出は対象作業の実装と、その段階で必要な検証・提出物が揃った時点で行う。承認待ちの作業が`complete`であることを提出条件にして、承認と完了の循環待ちを作らない。

モックとの差分、既知の問題、検証済み／未検証の範囲も提示する。ユーザーが共通設計を承認してから残りの画面へ展開する。判断待ちの間も、共通設計の承認に依存しない作業は進めてよい。

全画面レビューでは画面間の一貫性、資料4の検証結果・残件を提示する。指摘を作業へ戻し、修正した範囲とその影響を再検証する。後の修正で承認済みの共通設計を変更する場合、その影響範囲を再レビューする。レビュー待ちの対象範囲を明示し、無関係な部分まで一律に最初からやり直さない。

## 承認した変更と検証の更新（Q8）

- 判断の経緯は進捗JSONの指摘・レビューに記録し、現在の仕様・理由は該当する要件文書へ反映する。変更箇所から判断IDを参照できるようにする。
- 比較基準は凍結モックと、資料4の既存の合意、およびその後に承認した変更とする。承認した差分は判断IDに結び付け、単なる再現漏れと区別する。資料間の未解決の矛盾は、実装者が都合のよい方を選ばず判断を求める。
- 検査の期待値や比較画像は、承認済みの変更に合わせて更新する。検査を通すことだけを理由に更新しない。
- 共通トークン・部品などの変更で過去の検証結果が有効でなくなった場合、影響する作業の`verification_status`を`stale`にし、完了済みなら`implemented`へ戻す。必要な再検証・再レビューを作業へ反映する。過去の証拠は履歴として残す。

## 継続的な参照と開始用プロンプト（Q9）

規律の本文は本資料に集約する。[AGENTS.md](../AGENTS.md)には、テーマ実装・移行作業時に資料3〜5と進捗JSONを読む参照指示を置く。[開始用プロンプト](07-theme-implementation-goal.md)は、目標・参照先・進捗更新・レビュー条件・完了条件を指示する。詳細を重複させず、開始時・再開時とも同じ文書へ戻れるようにする。
