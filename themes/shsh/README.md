# shsh

控えめな装飾で本文へ集中できる、日本語の技術文書のためのHugoテーマ。
ミニマルかつタイポグラフィを強調したデザイン体系で、技術記事の長文・コード・図表を明瞭に読み進められるテーマを目指す。

日記や写真も技術記事と同じデザインで扱う。単一言語サイトを対象とし、固定UIは短い英語、本文・タイトル・分類名は書き手の言語を保つ。

## コンセプトと情報設計

デザインの基準は記事本文とする。PaperModのミニマルさを出発点に、和欧文の混植、見出し、余白を日本語の読書に合わせる。

| 場所                         | 役割・判断理由                                                                   |
| ---------------------------- | -------------------------------------------------------------------------------- |
| ホーム                       | 短い紹介から新着記事へつなぐ。著者個人よりサイトと記事を主役にする               |
| About                        | 継続的に更新・共有する著者紹介。鮮度や反応を記事と共通の考え方で扱う             |
| 記事一覧・個別タグ／カテゴリ | 関心に合う記事を選ぶため、要約やカバーを添える。分類は話題から記事への入口とする |
| Archives                     | 時期やタイトルの記憶から探すため、記事一覧より情報を絞る                         |
| 記事詳細                     | 本文を読み進め、読後に分類・共有・前後の記事へつなぐ                             |
| フッター                     | 著者の活動や継続的な購読への入口。個々の記事を共有する操作と分ける               |

一覧と記事間移動は、新着から過去へ進む流れを共通にする。左のPrevは新しい記事、右のNextは古い記事とし、方向の意味を保つ。日付は鮮度の判断材料とし、公開日と更新日が同じ年月日なら時刻差は区別しない。

共有は記事を外へ届ける操作、はてなスターは記事に付く反応として扱う。共有の外観はサイトに揃え、スターは公式ウィジェットの性質を尊重する。RSSは継続して読むための入口とし、テーマ変更後も既存の購読先や記事への参照を引き継ぐ。

## 書体・組版・操作性

端末に備わる書体を基本とし、端末間の字形の違いは許容する。書体選定には次の理由がある。

- Apple環境はSan Franciscoとヒラギノ、WindowsはSegoe UIとNoto Sans JPを想定する。Apple標準指定だけでは和文がヒラギノになるとは限らず、Windowsでは游ゴシックのかすれを避けたいので、`system-ui`への一括委任はしない。
- コード用の候補は本文と分ける。本文用の和文候補を共有すると、欧文用コード書体がない環境でプロポーショナルな欧文が選ばれるため。
- Windows 11のFirefoxで見出しのウェイト500指定が通常書体になる差異があるが、サイズでも階層を識別できるため許容する。本文サイズはSafariで和文が小さく見える点、コード行高はWindows（Consolas）で行間が詰まって見える点を踏まえて調整している。

見出し・補助文字・大きな余白は本文基準のモジュラースケール、操作部品は独立した寸法の尺度を持つ。本文のリズムと操作性を別々に調整し、どちらも読者の文字サイズ設定に追従させる。行高は本文・見出し・ラベル・表・コードの役割別に持ち、数値の一致だけを理由にまとめない。

構造を区切る余白は、文字サイズのスケール5段分に当たる1.6倍刻みで広げる。近い値を用途ごとに増やさず、関係の強さに応じて次の4段階を使う。補助文字の中でも本文サイズを基準にし、区切りの強さを保つ。

| トークン          | 本文サイズ比（17px時） | 用途                                                                                                                                     |
| ----------------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `--space-block`   | 1.6（約27px）          | 引用・図表・コードの前後、記事ヘッダーと本文、カバー、記事フッター内の各グループ、ナビの区切り線の内側、Archivesの年見出しと月のまとまり |
| `--space-section` | 2.56（約44px）         | 本文と記事フッター、脚注、本文中の区切り線、一覧見出しと内容、一覧の区切り線の両側、サイトヘッダーの上下                                 |
| `--space-group`   | 4.096（約70px）        | ホームの紹介と記事一覧、Archivesの年同士、一覧とページ送り                                                                               |
| `--space-page`    | 6.554（約111px）       | ページ内容の末尾とサイトフッター                                                                                                         |

本文からタグや共有操作へは記事内の区切り、サイトフッターへは記事を離れる区切りとして、後者を広く取る。前後記事ナビや共有操作の有無によらず、ページ末尾には同じ最小余白を確保する。短いページではフッターの自動マージンが画面の残りを吸収する。記事フッター内は存在するグループの間だけに余白を置き、最後のタグやナビの有無で末尾に余白を足さない。

段落の1em、リストのその分数、見出し自身のサイズに比例する前後余白は、本文を読み進める局所的なリズムとして維持する。本文の先頭・末尾の外側余白は取り除き、周囲の構造が境界の余白を決める。アイコン・操作領域・メタデータなど部品内の余白には4px刻みのUIグリッドを使う。

ライト・ダークを同等に扱い、[Catppuccin Latte／Mocha](https://catppuccin.com/palette/)で文章とコードの配色を揃える。公式のシンタックスハイライトとコード背景を維持し、ページ側で調整する。一部のコード色にはコントラスト上の制約があり、axeの例外もChromaのコード色に限定する。

アイコンや補助操作は控えめにし、図柄の大きさと操作領域を分けて押しやすさを保つ。キーボードのフォーカスは明確にする。見出しリンクは節の共有を助けるものとして、特にタッチ環境での存在感を抑える。画像は見かけの高さを揃えるより、図やスクリーンショットの情報と縦横比を保つことを優先する。

## 画像加工

処理は[media/image-data.html](layouts/_partials/media/image-data.html)に集約する。page bundleまたは`assets/`の画像を対象とし、切り抜きや拡大はしない。

| 対象                                      | 処理                                                                                                 |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| PNG・GIF                                  | Catmull-Romで縮小し、元画像から直接、可逆WebPを生成                                                  |
| WebP                                      | 先頭のチャンクで可逆・非可逆を判定し、同じ圧縮方式のWebPを生成。原寸幅の候補には元画像をそのまま使う |
| JPEG・その他の処理可能な静止画像          | `imaging.resampleFilter`で縮小し、元画像から直接、非可逆WebPを生成。品質は`imaging.webp`設定         |
| SVG・アニメーション・static参照・外部画像 | 加工しない。外部画像はビルド時にも取得しない                                                         |

PNG・GIFはスクリーンショットや図、それ以外は写真が多いという前提で圧縮方式を選ぶ。グレースケール画像はHugoのWebP変換で明るさがわずかに変わるが、形式ごとの例外を増やさず許容する。

候補の選択は次の順で行う。

1. 原寸未満の360・720・1080・1440px幅と、原寸幅を候補にする。原寸幅は1440px超でも含める。
2. より広い候補の容量以下になる候補を除外する。縮小で中間色が増えたパレット画像は、原寸幅の可逆WebPより重くなることがある。除外した候補は公開しない。
3. 残った候補を`picture`内の`source type="image/webp"`に並べ、ブラウザに選択を委ねる。`img`には`srcset`を付けず、`src`を元画像、取得できた寸法も出力する。WebP非対応のブラウザは`source`を飛ばして元画像を表示する。

元画像との容量比較はしない。ブラウザは`source`を選んだ後で元画像に戻らないため、候補を除外しても、より広いWebPが選ばれるだけになる。広い候補を選ぶ除外は転送量を減らすが、デコードする画素数は増えることがある。

## 開発と検査

サイト生成はHugoだけで完結し、Node.jsとpnpmは開発・検査に使う。Node.jsは[.node-version](.node-version)、pnpmは[package.json](package.json)の指定に合わせる。

`themes/shsh`で実行する。

```sh
pnpm install --frozen-lockfile
pnpm exec playwright install chromium firefox webkit
pnpm check
```

整形は`pnpm format`を使う。`pnpm check`はlint、Hugo生成、HTML/XML、Chromium・Firefox・WebKitの表示・操作を検査する。

検査入力は実記事のコピーを含め`tests/fixtures/`に置き、ブログ本体の設定やファイルは参照しない。出力は`.cache/`に置く。外部埋め込みは固定のshortcodeへ置換し、ブラウザの外部通信も遮断する。

`pnpm check`の実行後、画面fixtureをローカルでプレビューできる。

```sh
hugo server --source .cache/screens/source --themesDir "$(pwd)/.."
```

表示・操作の変更時は、OS固有フォントやSafari・モバイル実機、外部埋め込みの動作も別途確認する。

設定例は[画面fixtureのhugo.json](tests/fixtures/screens/hugo.json)を参照する。
