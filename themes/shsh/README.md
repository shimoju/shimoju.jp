# shsh

控えめな装飾で本文へ集中できる、日本語の技術文書のためのHugoテーマ。
ミニマルかつタイポグラフィを強調したデザイン体系で、技術記事の長文・コード・図表を明瞭に読み進められるテーマを目指す。

日記や写真も技術記事と同じデザインで扱う。単一言語サイトを対象とし、固定UIは短い英語、本文・タイトル・分類名は書き手の言語を保つ。

## コンセプトと情報設計

デザインの基準は記事本文とする。PaperModのミニマルさを出発点に、和欧文の混植、見出し、余白を日本語の読書に合わせる。

| 場所                         | 役割・判断理由                                                                   |
| ---------------------------- | -------------------------------------------------------------------------------- |
| ホーム                       | 短い紹介から新着記事へつなぐ。著者個人よりサイトと記事を主役にする               |
| About                        | 継続的に更新・共有する著者紹介。鮮度や反応を記事と共通の考え方で扱う             |
| 記事一覧・個別タグ／カテゴリ | 関心に合う記事を選ぶため、要約やカバーを添える。分類は話題から記事への入口とする |
| Archives                     | 時期やタイトルの記憶から探すため、記事一覧より情報を絞る                         |
| 記事詳細                     | 本文を読み進め、読後に分類・共有・前後の記事へつなぐ                             |
| フッター                     | 著者の活動や継続的な購読への入口。個々の記事を共有する操作と分ける               |

一覧と記事間移動は、新着から過去へ進む流れを共通にする。左のPrevは新しい記事、右のNextは古い記事とし、方向の意味を保つ。日付は鮮度の判断材料とし、公開日と更新日が同じ年月日なら時刻差は区別しない。

共有は記事を外へ届ける操作、はてなスターは記事に付く反応として扱う。共有の外観はサイトに揃え、スターは公式ウィジェットの性質を尊重する。RSSは継続して読むための入口とし、テーマ変更後も既存の購読先や記事への参照を引き継ぐ。

## 書体・組版・操作性

端末に備わる書体を基本とし、端末間の字形の違いは許容する。書体選定には次の理由がある。

- Apple環境はSan Franciscoとヒラギノ、WindowsはSegoe UIとNoto Sans JPを想定する。Apple標準指定だけでは和文がヒラギノになるとは限らず、Windowsでは游ゴシックのかすれを避けたいので、`system-ui`への一括委任はしない。
- コード用の候補は本文と分ける。本文用の和文候補を共有すると、欧文用コード書体がない環境でプロポーショナルな欧文が選ばれるため。
- Windows 11のFirefoxで見出しのウェイト500指定が通常書体になる差異があるが、サイズでも階層を識別できるため許容する。本文サイズはSafariで和文が小さく見える点、コード行高はWindows（Consolas）で行間が詰まって見える点を踏まえて調整している。

見出し・補助文字・大きな余白は本文基準のモジュラースケール、操作部品は独立した寸法の尺度を持つ。本文のリズムと操作性を別々に調整し、どちらも読者の文字サイズ設定に追従させる。行高は本文・見出し・ラベル・表・コードの役割別に持ち、数値の一致だけを理由にまとめない。

ライト・ダークを同等に扱い、[Catppuccin Latte／Mocha](https://catppuccin.com/palette/)で文章とコードの配色を揃える。公式のシンタックスハイライトとコード背景を維持し、ページ側で調整する。一部のコード色にはコントラスト上の制約があり、axeの例外もChromaのコード色に限定する。

アイコンや補助操作は控えめにし、図柄の大きさと操作領域を分けて押しやすさを保つ。キーボードのフォーカスは明確にする。見出しリンクは節の共有を助けるものとして、特にタッチ環境での存在感を抑える。画像は見かけの高さを揃えるより、図やスクリーンショットの情報と縦横比を保つことを優先する。

## 画像加工

処理は[media/image-data.html](layouts/_partials/media/image-data.html)に集約する。page bundleまたは`assets/`の画像を対象とし、切り抜きや拡大はしない。

| 対象                                      | 処理                                                       |
| ----------------------------------------- | ---------------------------------------------------------- |
| PNG（下記の例外を除く）                   | 元画像から直接、可逆WebPを生成                             |
| JPEG                                      | 元画像から直接、品質80の非可逆WebPを生成                   |
| その他の処理可能な静止画像                | 元形式で縮小。原寸幅の候補には再エンコードせず原画像を使う |
| グレースケールPNG                         | 加工しない。HugoのWebP変換で明るさが変わるため             |
| SVG・アニメーション・static参照・外部画像 | 加工しない。外部画像はビルド時にも取得しない               |

候補の選択は次の順で行う。

1. 原寸以下の360・720・1080・1440px幅を候補にする。原寸が1440px以下なら、原寸幅も含める。
2. 変換・縮小で元画像の容量以上になった候補を除外する。除外があり、原寸幅の候補が残っていなければ原画像を追加する。この場合は1440px超でも追加する。
3. 幅が重複しない候補を`img srcset`に並べ、ブラウザに選択を委ねる。`img src`は元画像とし、取得できた寸法も出力する。

## 開発と検査

サイト生成はHugoだけで完結し、Node.jsとpnpmは開発・検査に使う。Node.jsは[.node-version](.node-version)、pnpmは[package.json](package.json)の指定に合わせる。

ローカルプレビューはリポジトリのルートから起動する。

```sh
bin/dev
```

開発環境の準備と一括検査は`themes/shsh`に移動して実行する。

```sh
cd themes/shsh
pnpm install --frozen-lockfile
pnpm exec playwright install chromium firefox webkit
pnpm check
```

以降は`themes/shsh`内で、整形に`pnpm format`、一括検査に`pnpm check`を使う。検査にはlint、Hugo生成、HTML/XML、Chromium・Firefox・WebKitの表示・操作を含む。

検査入力は`tests/fixtures/`とサイトの実記事を使い、出力は`.cache/`へ隔離する。通常CIでは外部埋め込みを固定のshortcodeへ置換し、ブラウザの外部通信も遮断するため、外部サービスの動作は検証しない。

表示・操作の変更時は、Playwrightで保証できないOS固有フォントやSafari・モバイル実機も確認する。外部埋め込みは本番相当ビルドとpreviewで、表示・動画再生・スライド送りを確認する。

実装は`assets/`・`layouts/`、設定は[hugo.yml](../../hugo.yml)を参照する。執筆・ビルド・配信は[サイトのREADME](../../README.md)にまとめる。
